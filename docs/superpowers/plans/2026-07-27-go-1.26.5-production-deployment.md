# Go 1.26.5 Production Deployment Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Upgrade the existing Vercel Go service to Go 1.26.5 and publish a verified production deployment.

**Architecture:** Vercel reads the root `go.mod` directive to select the Go runtime, so the implementation changes only active version metadata. The service is verified locally with Go 1.26.5 before the existing Vercel project is linked, deployed to production, inspected, and health-checked.

**Tech Stack:** Go 1.26.5, Go modules, Vercel Go Functions, Vercel CLI

## Global Constraints

- The required Go version is exactly 1.26.5.
- Application behavior, Go dependencies, and handler source code must remain unchanged unless verification exposes a Go 1.26.5 compatibility failure.
- Do not add a `toolchain` directive or custom Vercel runtime configuration.
- Do not create a new Vercel project; stop for user direction if the existing project is ambiguous.
- Historical specifications and implementation plans retain their original Go version references.
- Production deployment requires successful local test, build, and vet commands first.

### Task 1: Update Active Go Version Metadata

**Files:**
- Modify: `go.mod`
- Modify: `AGENTS.md`
- Modify: `CLAUDE.md`

**Interfaces:**
- Consumes: Vercel's root `go.mod` runtime detection and the installed `go1.26.5` toolchain.
- Produces: Active project metadata that consistently requires Go 1.26.5.

- [ ] **Step 1: Confirm the expected pre-upgrade declarations**

Run:

```bash
rg -n '1\.24(\.5|\.x)' go.mod AGENTS.md CLAUDE.md
```

Expected: `go.mod` reports `go 1.24.5`, while `AGENTS.md` and `CLAUDE.md`
report Go 1.24.x.

- [ ] **Step 2: Change the three active declarations**

Apply this exact patch:

```diff
--- a/go.mod
+++ b/go.mod
@@
-go 1.24.5
+go 1.26.5
--- a/AGENTS.md
+++ b/AGENTS.md
@@
-- Target Go `1.24.x`. Use `gofmt -w` before committing; prefer organizing imports via `goimports` if available.
+- Target Go `1.26.5`. Use `gofmt -w` before committing; prefer organizing imports via `goimports` if available.
--- a/CLAUDE.md
+++ b/CLAUDE.md
@@
-- Go 1.24.x target
+- Go 1.26.5 target
```

- [ ] **Step 3: Confirm module metadata remains tidy**

Run:

```bash
GOCACHE=$(pwd)/.cache/go-build go mod tidy
git diff --exit-code -- go.sum
```

Expected: `go mod tidy` succeeds and `go.sum` has no changes.

- [ ] **Step 4: Verify active and historical version references**

Run:

```bash
rg -n 'go 1\.26\.5|Go `1\.26\.5`|Go 1\.26\.5' go.mod AGENTS.md CLAUDE.md
rg -n '1\.24(\.5|\.x)' go.mod AGENTS.md CLAUDE.md
```

Expected: the first command finds one declaration in each active file; the
second command returns no matches. References under `docs/superpowers/` are
not part of this check because they describe historical work.

- [ ] **Step 5: Run the full Go 1.26.5 verification suite**

Run:

```bash
go version
GOCACHE=$(pwd)/.cache/go-build go test ./...
GOCACHE=$(pwd)/.cache/go-build go build ./...
GOCACHE=$(pwd)/.cache/go-build go vet ./...
git diff --check
```

Expected: `go version` reports `go1.26.5`; all packages test, build, and vet
successfully; the diff has no whitespace errors.

- [ ] **Step 6: Commit the version upgrade**

Run:

```bash
git add go.mod AGENTS.md CLAUDE.md
git commit -m "chore: upgrade go to 1.26.5"
```

Expected: one commit containing only the three active metadata files.

### Task 2: Deploy the Existing Vercel Project to Production

**Files:**
- Local-only project link: `.vercel/project.json`

**Interfaces:**
- Consumes: The verified Task 1 commit, an authenticated Vercel account, and the existing Vercel project.
- Produces: A successful production deployment URL serving the Go 1.26.5 build.

- [ ] **Step 1: Obtain the Vercel CLI and verify authentication**

Run:

```bash
npx --yes vercel@latest --version
npx --yes vercel@latest whoami
```

Expected: the CLI prints its version and the authenticated Vercel username. If
authentication is missing, stop and ask the user to authorize `vercel login`.

- [ ] **Step 2: Identify the existing project before linking**

Run:

```bash
git remote -v
npx --yes vercel@latest project ls
```

Expected: exactly one listed project clearly corresponds to the repository
remote. If no project or multiple plausible projects are found, stop and ask
the user to identify the target; do not create a project.

- [ ] **Step 3: Link the verified workspace to that existing project**

Run:

```bash
npx --yes vercel@latest link
```

Choose the authenticated scope and the exact existing project identified in
Step 2. Confirm `.vercel/project.json` contains the returned opaque project and
organization IDs. Do not commit `.vercel/`, which is ignored by the repository.

- [ ] **Step 4: Create the production deployment**

Run:

```bash
VERCEL_GO_DEPLOYMENT_URL=$(npx --yes vercel@latest --prod)
printf '%s\n' "$VERCEL_GO_DEPLOYMENT_URL"
```

Expected: the command uploads the verified working tree, completes the build,
and stores the production deployment URL in `VERCEL_GO_DEPLOYMENT_URL`.

- [ ] **Step 5: Inspect the deployment until it reaches a terminal state**

Run:

```bash
npx --yes vercel@latest inspect "$VERCEL_GO_DEPLOYMENT_URL" --wait
```

Expected: the deployment status is `Ready`. If it is `Error` or `Canceled`,
capture the inspection output and stop without claiming success.

- [ ] **Step 6: Verify the production health endpoint**

Run:

```bash
curl --fail-with-body --silent --show-error \
  --write-out '\nHTTP %{http_code}\n' \
  "$VERCEL_GO_DEPLOYMENT_URL/api/ping"
```

Expected: the endpoint returns the service's expected health body and an HTTP
2xx status.

- [ ] **Step 7: Record final repository and deployment evidence**

Run:

```bash
git status --short --branch
git log -3 --oneline --decorate
npx --yes vercel@latest inspect "$VERCEL_GO_DEPLOYMENT_URL"
```

Expected: no unintended tracked changes, the Go 1.26.5 commit is visible, and
Vercel still reports the production deployment as `Ready`.
